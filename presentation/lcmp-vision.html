LCMP Vision — Event-Driven Orchestration
No central orchestrator. Jira IS the control plane. Git IS the state machine.

The Idea

Jira Board = Migration Control Plane

Every migration phase is an EPIC. Every step (or step × workpackage) is a STORY. The board is the single source of truth for what's done, what's in progress, and what's next.

Event Loop, Not Central Steering

An independent watcher process monitors the Jira board for status changes. When a ticket moves to "Ready" or "Approved", the watcher picks it up, marks it "In Progress", delegates to the right agent, and sets it to "Done" when complete. No supervisor agent. No orchestrator. Just events.

Human-in-the-Loop = Change a Ticket Status

To approve a deliverable: move the ticket to "Approved". To reject: move to "Rejected" with a comment. To pause: leave it in "Review". The human interacts with the migration through the same tool they use for everything else.

Git Tags = Checkpoints

Every ticket is linked to a git tag on creation (LCMP-123/started) and on completion (LCMP-123/completed). Full traceability. Any point in the migration can be restored from a tag.

Core Principle

The migration is not a program that runs. It's a board that evolves. Agents react to board events. Humans steer by moving tickets.

Ticket Lifecycle

1
lcmp init creates all epics + stories with dependencies. Board is populated.
2
Phase 1 stories auto-set to "Ready" (no dependencies).
3
Watcher picks up "Ready" → marks "In Progress" → creates git tag → delegates to agent.
4
Agent completes → watcher marks "Review" → creates git tag.
5
Human reviews deliverables (on disk or in dashboard). Moves ticket to "Approved" or "Rejected".
6
If approved → watcher unblocks dependent stories → they become "Ready" → loop continues.
7
If rejected → watcher creates remediation sub-ticket linked to original → agent re-executes with feedback.

Dependency Resolution

Each story has Jira "blocked by" links. The watcher only sets a story to "Ready" when all its blockers are "Approved". This replaces the phase sequencing logic in the orchestrator — Jira's dependency graph IS the state machine.

Event Watcher Process

LCMP Event Watcher (long-running process) │ ├── STARTUP │ └── Connect to Jira API (webhook or poll interval) │ Connect to Git repo (local) │ Load agent registry (which agent handles which step type) │ ├── EVENT: ticket_status → "Ready" │ ├── 1. Validate: all "blocked by" tickets are "Approved" │ ├── 2. Transition ticket → "In Progress" │ ├── 3. Git tag: LCMP-{ticket-id}/started │ ├── 4. Resolve agent: step_type → agent_name │ │ e.g., "business_context" → business_specialist_requirements │ ├── 5. Build context: read ticket metadata (WP-ID, phase, step) │ │ Load prompt file for this step type │ │ Inject WP-specific context │ ├── 6. Delegate to agent (Kiro CLI / Pydantic AI / Bedrock) │ ├── 7. On agent completion: │ │ ├── Run deliverable_validator.py │ │ ├── Git add + commit deliverables │ │ ├── Git tag: LCMP-{ticket-id}/completed │ │ ├── Attach deliverable paths to ticket │ │ └── Transition ticket → "Review" │ └── 8. On agent failure: │ ├── Transition ticket → "Failed" │ ├── Attach error log to ticket │ └── Alert human (Jira notification) │ ├── EVENT: ticket_status → "Approved" │ ├── 1. Git tag: LCMP-{ticket-id}/approved │ ├── 2. Find all tickets blocked by this one │ ├── 3. For each blocked ticket: │ │ Check if ALL its blockers are now "Approved" │ │ If yes → transition to "Ready" │ └── 4. Log: "Unblocked N tickets" │ ├── EVENT: ticket_status → "Rejected" │ ├── 1. Read rejection comment from ticket │ ├── 2. Create sub-ticket: "{original title} - Remediation" │ │ Link to original ticket │ │ Attach rejection feedback │ │ Set status → "Ready" │ └── 3. Watcher picks up sub-ticket → agent re-executes │ └── EVENT: ticket_status → "Paused" └── No action. Human controls when to resume. Move to "Ready" when ready to continue.

Git Tag Strategy

LCMP-{id}/started

Created when agent begins work. Tags the repo state before any changes. Enables rollback to pre-step state if agent produces bad output.

LCMP-{id}/completed

Created when agent finishes and deliverables pass validation. Tags the repo state with all new deliverables committed. This is the "candidate" state awaiting human review.

LCMP-{id}/approved

Created when human approves the ticket. Tags the exact commit that was approved. Downstream tickets can now reference this tag as their baseline.

Why This Works

No Central Orchestrator

The watcher is stateless — it reacts to events. If it crashes, restart it. It reads the board state and picks up where it left off. No conversation context to lose. No state file to corrupt.

Natural Parallelism

If WP-001 and WP-003 are both "Ready" (no mutual dependencies), the watcher delegates both to agents simultaneously. Parallelism emerges from the dependency graph — no explicit pod partitioning needed for simple cases.

Human Pace, Not Machine Pace

The migration runs as fast as humans approve. Leave tickets in "Review" for a week — no timeout, no idle cost. Approve 10 at once — agents fan out immediately. The board adapts to the team's rhythm.

Full Audit Trail

Every action is a Jira ticket transition + a git tag. Who approved what, when, with what feedback — all in Jira history. What code was produced at each step — all in git tags. Complete traceability without any custom tooling.

Implementation Path
From current state to event-driven orchestration — incremental, not big-bang

Phase 1: Board Initialization (lcmp init)

What it does

lcmp init --project carddemo --tracker jira

1. Reads project-config.json + phase definitions
2. Creates Jira project with board
3. Creates one Epic per phase
4. Creates Stories per step (or step × WP for Phases 3–5)
5. Sets "blocked by" links based on phase dependencies
6. Tags Phase 1 stories as "Ready"
7. Git tag: lcmp/initialized

Phase 2: Event Watcher

Minimal viable watcher

Python process. Polls Jira every 30s (upgrade to webhooks later).
Handles 3 events: Ready → delegate, Approved → unblock, Rejected → remediate.
Agent delegation via Kiro CLI, Pydantic AI, or direct Bedrock calls.
Git operations via subprocess (same as today).

Phase 3: GitHub Integration

Bidirectional linking

Every git tag references the Jira ticket ID.
Every Jira ticket links to the git tag/commit.
PR creation on phase completion (optional).
GitHub Actions can trigger on tag creation for CI/CD.

Key Insight

This is not a rewrite. The prompts, agents, templates, validators, and git workflow are unchanged. We're replacing the orchestration layer (Python state machine or human-in-Kiro) with an event-driven watcher that reads from Jira. Everything else stays.

Compatibility

All three modes can coexist:
Kiro-CLI: Human drives via chat (current)
Standalone: Python orchestrator drives (current)
Event-driven: Jira board drives (future)

Same prompts, same agents, same deliverables. Different control plane.
